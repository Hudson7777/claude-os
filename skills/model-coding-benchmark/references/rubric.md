# 评分标准

## 每题评分（5维加权 = 50分/题，6题总分300分）

| 维度 | 满分 | 说明 |
|------|------|------|
| 正确性 | 15 | 代码是否产生正确结果（最高权重） |
| 完整性 | 12 | 是否满足所有需求 |
| 工具使用 | 10 | 是否正确使用工具（读文件、运行、验证） |
| 代码质量 | 8 | 风格、结构、可维护性 |
| 效率 | 5 | 速度 + 成功率 |

### 客观锚点（T2/T5/T6）

T2、T5、T6 有 ground truth 验证脚本（`verify_t2.py`、`verify_t5.py`、`verify_t6.py`）。
在 Step 3 收集结果时自动运行，结果作为正确性打分的硬性上限：

| verify 结果 | 正确性上限 |
|-------------|-----------|
| VERIFY: PASS（全部通过） | 无上限（盲评正常打分） |
| VERIFY: FAIL（部分失败） | 最高 9 分（有客观错误存在） |
| 无法运行 / 导入报错 | 最高 6 分 |

T1、T3、T4 无验证脚本，正确性完全由盲评打分。

---

### 1. 正确性（0-15）

代码是否产生正确结果。

| 分数 | 标准 |
|------|------|
| 15 | 完全正确，无任何问题 |
| 13-14 | 正确但有小瑕疵（如格式不完美） |
| 11-12 | 基本正确，但有根因分析偏差或过度修复 |
| 9-10 | 大部分正确，有一个非关键错误 |
| 6-8 | 有明显错误但核心逻辑正确 |
| 2-5 | 严重错误，核心逻辑有问题 |
| 0-1 | 未产出或完全错误 |

**关键区分点**：
- T3 Debug：精准定位根因（如"auth_middleware未注册"）vs 过度设计（如"框架不支持路由级中间件"），即使结果都能通过测试，后者正确性应低于前者
- T1 代码生成：salary 用 float vs int 丢失精度，后者正确性扣分
- T5 重构：原地 merge 导致 O(n²) 退化，如未在 docstring 标注则扣分
- T2 二轮修复：一轮通过得满分，二轮通过扣 2 分，未通过按实际修复数量比例打分

### 2. 完整性（0-12）

是否满足所有需求。

| 分数 | 标准 |
|------|------|
| 12 | 所有需求全部满足 |
| 10-11 | 满足但有1个小遗漏 |
| 8-9 | 满足大部分，缺少1个非核心需求 |
| 5-7 | 缺少2-3个需求 |
| 2-4 | 只满足少部分需求 |
| 0-1 | 未完成或未产出 |

**关键区分点**：
- T6：6个需求是否全部实现（CRUD + 过滤 + 分页 + 日志中间件 + 错误中间件）
- T5：5个要求是否全部满足（原地排序 + 泛型 + 类型注解 + docstring + 测试通过）
- T2：是否展示完整的 读→运行→定位→修复→验证 过程

### 3. 工具使用（0-10）

是否正确使用工具（读文件、运行、验证）。

| 分数 | 标准 |
|------|------|
| 10 | 完整工具链：读取→运行→定位→修复→回归测试→二次验证，过程透明 |
| 8-9 | 使用了主要工具但过程不够透明 |
| 6-7 | 使用了部分工具，缺少验证步骤 |
| 4-5 | 工具使用有但不充分 |
| 1-3 | 几乎未使用工具 |
| 0 | 未使用工具或未产出 |

**关键区分点**：
- T2 是工具使用的核心测试题：是否实际运行并展示报错？是否列出具体 bug？是否写回归测试？
- 过程透明度：仅说"6个bug已修复，测试通过" vs 展示完整证据链

### 4. 代码质量（0-8）

代码风格、结构、可维护性。

| 分数 | 标准 |
|------|------|
| 8 | 生产级：类型注解完整、分层清晰、命名规范、路径处理规范（pathlib） |
| 6-7 | 良好：结构清晰，但缺类型注解或有不规范之处 |
| 4-5 | 可用：功能实现但代码粗糙，缺少抽象 |
| 2-3 | 凑合：有死代码、重复逻辑、命名混乱 |
| 1 | 差：结构混乱、硬编码、不可维护 |
| 0 | 不可读或未产出 |

**关键区分点**：
- 类型注解（Py3.9+ `list[dict]` vs 无注解）
- 路径处理（`Path(__file__).with_name()` vs 硬编码字符串）
- 框架扩展方式（继承 vs monkey-patch，前者通常更干净）
- 死代码/冗余逻辑（如两次 patch handle）

### 5. 效率（0-5）

速度 + 成功率的综合评估。效率分 = 速度分（0-4）+ 成功率分（0-1）。

**速度分按任务难度分档：**

| 任务 | 速度分4（快） | 速度分3 | 速度分2 | 速度分1（慢） | 速度分0 |
|------|------------|---------|---------|------------|---------|
| T1 代码生成 | <2min | 2-4min | 4-7min | 7-15min | >15min或TIMEOUT |
| T4 代码理解 | <2min | 2-4min | 4-7min | 7-15min | >15min或TIMEOUT |
| T2 工具调用 | <5min | 5-8min | 8-12min | 12-20min | >20min或TIMEOUT |
| T3 Debug | <5min | 5-8min | 8-12min | 12-20min | >20min或TIMEOUT |
| T5 重构 | <5min | 5-8min | 8-12min | 12-20min | >20min或TIMEOUT |
| T6 综合实战 | <8min | 8-12min | 12-18min | 18-25min | >25min或TIMEOUT |

**成功率分：**

| 结果状态 | 成功率分 |
|----------|----------|
| 完全成功 | 1 |
| 部分成功（功能完成但有瑕疵） | 0.5 |
| 失败但有输出 / TIMEOUT | 0 |

**跨模型对比时**：如果所有模型都在同一时间段内完成，可相对打分——最快者速度分4，次者2-3，最慢者1。

## 多盲评聚合

使用3个不同评测模型盲评，取平均分：

```
某题某维度最终分 = (评测者1打分 + 评测者2打分 + 评测者3打分) / 3
某题最终分 = sum(5个维度最终分)
某模型总分 = sum(6题最终分)
```

如果某个评测者结果缺失，用其余评测者的平均分代替。
